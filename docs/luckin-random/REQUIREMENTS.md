三、核心功能：候选咖啡池
━━━━━━━━━━━━━━━━━━━━

这是整个项目最重要的功能。

用户第一次使用时：

1. 登录并授权瑞幸账号。
2. 选择城市和常用门店。
3. 获取该门店的实时商品菜单。
4. 按官方可用能力展示商品分类、名称、图片和价格。
5. 允许搜索具体饮品。
6. 用户可以从菜单中勾选多款喜欢的饮品。
7. 将选中的饮品加入“我的咖啡池”。

咖啡池功能：

- 添加饮品
- 删除饮品
- 编辑饮品
- 暂时禁用某款饮品
- 查看饮品详情
- 保存到本地
- 支持恢复配置
- 支持多个咖啡池
- 可以随时更改候选集合

每款饮品需要独立记录：

- 商品名称
- 商品 ID
- SKU 或规格标识
- 杯型
- 温度
- 糖度
- 冰量
- 其他可配置属性
- 用户自定义备注
- 随机权重
- 是否启用

不同咖啡可以有不同配置。

例如：

生椰拿铁：大杯、冰、少糖
丝绒拿铁：大杯、冰
厚乳拿铁：大杯、热
橙C美式：大杯、冰

上述仅为配置示例。

真实菜单、商品 ID、SKU 和可选规格必须通过官方接口获取，不得硬编码。

保存的 SKU 仅用于标识用户偏好。每次下单前必须重新检查对应门店的有效商品和规格。

四、随机选品算法
━━━━━━━━━━━━━━━━━━━━

默认模式为等概率随机抽取。

例如候选池有五杯咖啡，每杯默认有 20% 的抽中概率。

需要实现：

1. 一键随机抽取。
2. 排除已经禁用的饮品。
3. 可选启用“避免连续两次重复”。
4. 可选启用加权随机。
5. 支持查看随机结果。
6. 支持查看历史抽取记录。
7. 支持查看每款饮品被抽中的次数。
8. 支持手动重新抽取。

加权随机示例：

生椰拿铁：40%
丝绒拿铁：30%
厚乳拿铁：20%
橙C美式：10%

默认仍使用完全等概率模式。

重要规则：

随机抽中某款饮品后，必须检查：

- 当前门店是否有售
- 商品是否缺货
- 规格是否仍然有效
- 当前是否可以购买
- 优惠后价格是否超出预算

如果不符合条件：

自动从尚未尝试过的有效候选中重新抽取。

每轮不得无限循环。

如果全部候选不可用：

停止下单并通知用户具体原因。

每次成功创建订单后，记录实际抽中的商品。

━━━━━━━━━━━━━━━━━━━━
五、自动下单
━━━━━━━━━━━━━━━━━━━━

用户可以选择：

模式 A：手动一键下单
模式 B：每天定时下单
模式 C：每周指定日期下单

手动模式：

用户点击“随机买一杯”。

程序自动：

1. 选择常用门店。
2. 获取候选咖啡池。
3. 随机抽取饮品。
4. 校验商品库存和规格。
5. 获取实时价格。
6. 查询可用优惠券。
7. 计算实付金额。
8. 检查消费限制。
9. 创建订单。
10. 进入支付流程。

整个过程不需要反复手动选择商品。

定时模式：

用户设置执行时间。

例如：
每天上午 9:00 随机买一杯咖啡。

系统在指定时间自动执行选品、优惠和订单创建。

注意：

- 必须使用正确的时区。
- 默认使用 Asia/Shanghai。
- 不依赖 iOS App 持续后台运行。
- 优先使用可靠的服务端调度。
- 允许暂停、恢复和关闭任务。
- 必须提供任务执行记录。
- 用户必须明确启用真实自动下单。

定时创建订单前，需要用户预先授权该模式并设置消费上限。

若订单需要用户付款，则发送通知，引导用户打开官方支付流程。

不得绕过用户的支付授权。

━━━━━━━━━━━━━━━━━━━━
六、自动优惠与预算
━━━━━━━━━━━━━━━━━━━━

每次创建订单前：

1. 获取商品实时售价。
2. 调用官方订单预览能力。
3. 检查官方返回的优惠券及优惠结果。
4. 按官方实际支持的方式使用优惠。
5. 计算最终实付金额。
6. 检查是否超过用户预算。

用户可以设置：

- 单杯最高价格
- 每日最高消费金额
- 每日最多下单数量
- 每周最大消费额度
- 每月最大消费额度

默认每天最多一单。

若超出预算：

优先尝试其他候选饮品。

如果全部超预算：

停止下单。

注意：

只使用瑞幸官方实际支持的优惠能力。

如果接口只能自动匹配优惠券，不支持自行选择最优券，必须如实说明。

不要声称已经实现无法验证的优惠策略。

七、支付系统：重点
━━━━━━━━━━━━━━━━━━━━

我愿意使用微信支付或者支付宝。

哪种方式可以实现更少的操作，就优先使用哪种。

我希望最终达到的体验：

打开 App 或点击快捷指令
→ 自动随机选咖啡
→ 自动计算优惠
→ 自动创建订单
→ 自动打开支付渠道
→ 我使用 Face ID 确认支付
→ 支付成功

理想情况下：

用户只需要主动触发一次点单，并完成一次支付身份验证。

无需人工重新选择饮品、门店或规格。

支付模块必须重点研究以下内容：

1. 瑞幸 MCP 创建订单后实际返回什么支付字段。
2. 是否返回二维码。
3. 是否返回官方 H5 支付链接。
4. 是否返回可用的 Universal Link。
5. 是否支持直接打开支付宝收银台。
6. 是否支持直接打开微信支付。
7. 能否在同一部 iPhone 上完成付款。
8. 是否可以调用官方支付渠道完成 Face ID 验证。

优先测试支付宝。

如果支付宝不支持，再测试微信。

如果微信更方便，则使用微信。

特别注意：

应用本身的 Face ID 认证不能替代微信或支付宝的付款授权。

不得模拟输入支付密码。
不得绕过支付验证。
不得伪造商户支付参数。
不得将普通二维码擅自转换成未经官方支持的支付请求。

如果官方只返回付款二维码：

必须提供可实际使用的备用支付方案，并明确说明哪些步骤还需要人工操作。

不要假装已经实现一键付款。

支付前需要保证订单金额符合用户预先设定的授权范围。

不得未经授权擅自提高金额。

十一、安全与可靠性
━━━━━━━━━━━━━━━━━━━━

由于涉及真实金钱，必须认真设计。

强制要求：

1. 默认禁止真实下单。
2. 开发测试默认使用模拟数据。
3. 只有我明确启用真实下单后才允许创建真实订单。
4. 默认最多每天一单。
5. 单次触发只允许创建一个有效订单。
6. 使用幂等控制防止重复创建。
7. 网络超时先检查订单状态。
8. 不确定订单是否成功时，禁止盲目重试。
9. 支持取消未支付订单，但需遵循官方允许的操作。
10. 记录所有订单状态变化。
11. 遇到支付失败不得重复扣款。
12. 所有价格与优惠以服务端官方结果为准。
13. 不能仅相信客户端传来的价格。
14. 认证 Token 必须安全存储。
15. 不得把 Token 写入 Git 仓库、普通日志或客户端公开配置。
16. 不存储微信、支付宝支付密码。
17. 生产环境通信使用 HTTPS。
18. 保护用户订单和个人信息。
19. 后端必须设置认证、访问控制和请求限流。
20. 定时任务必须支持紧急停止。

如果使用云端后端存储瑞幸 Token，需要实现安全存储、权限隔离、失效处理和撤销机制。

优先使用 GitHub Actions 的 macOS Runner 构建。

如果具备合法签名条件，构建可侧载的 IPA。

如果暂时没有证书：

也要完成可编译工程和自动化构建流程，并明确剩余的签名步骤。

不得声称未实际编译的工程已经构建成功。

不要把签名证书、私钥或账号密码提交到仓库。

十七、最终验收标准
━━━━━━━━━━━━━━━━━━━━

第一次使用：

登录瑞幸
→ 选择门店
→ 浏览菜单
→ 挑选几款咖啡
→ 配置各自规格

后续日常使用：

点击“随机买一杯”
→ 程序随机选择一款
→ 自动验证门店和商品
→ 自动使用可用优惠
→ 自动检查价格
→ 自动创建订单
→ 打开官方支付渠道
→ 我完成必要的支付验证
→ 自动显示取餐码

我还可以设置：

每天指定时间自动执行上述选品和订单流程，并在需要支付时通知我。

所有真实扣费都必须经过支付渠道合法授权。

项目必须可以持续使用，而不是一次性的演示程序。
